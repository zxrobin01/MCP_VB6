# VB6MCP 工具总览（工具面契约沙箱）

- 来源：docs/tools_schema.json（由维护者侧的快照工具从运行中的 add-in 抓取；本文件是生成物，勿手改） + bridge/hub_tools.json（hub 自有工具：ide_* 以及在 v1.11.0 迁到 tools/lessons.py 的 lessons 工具；同名时以 hub 定义为准）
- 数量：131（快照 120 + hub 追加 11；hub 覆盖同名 0）

## 使用顺序（工具集/描述变化后，按序执行并原样回贴输出）

```text
rem 1. 抓 live 快照并重冻：需要运行中的 add-in（自有实例；--url 必须显式给出），且需先经契约广播授权
rem --freeze 会写 docs/tools_schema.json 与冻结基线 tools/schema_baseline.json；只想预览就改用 --out 指向临时路径。
python tools/dump_tools_schema.py --freeze --url http://127.0.0.1:<your own port>/rpc
rem 2. 从 docs/tools_schema.json + bridge/hub_tools.json 重新生成本文件
python tools/export_tool_catalog.py
rem 3-4. 离线只读，可直接运行
python tools/check_schema_baseline.py
python tools/check_live_tools.py docs/tools_schema.json
rem 5. 严格 schema 审计：需要活着的 IDE（自有实例，端口 8767 及以上；8766 留给维护者自己的交互会话）
python tools/mcp_strict_audit.py --url http://127.0.0.1:<your own port>/mcp
```

## 冻结件与授权前提

- `tools/schema_baseline.json` 是**冻结件**：快照默认**不写**它；只有显式 `--freeze` 才写，且必须**先经契约广播**（版本号递增 + 每个受影响方的确认）。
- 禁止为了得到 `schema_changes=0` 就 `--freeze`——那会让基线比对退化为恒真。
- 数据源以 `docs/tools_schema.json`（live 快照）+ `bridge/hub_tools.json`（hub 自有工具）为准；**不要**解析 `integration/CodeTools.cls`（沙箱副本会滞后，曾致数量失真）。

| ide_state | Read the VB6 IDE mode RIGHT NOW (design/run/break) together with the raw VBA6 debug-engine flag, main window title, project name and a running flag. Never cached - a mode switch is visible on the very next call. The receipt ALWAYS carries inflight{active,tool,sinceMs,serviceable,kind} (who is in flight and whether it is a read or a write) and cancel{requested,applied,targetTool,targetKind,sinceMs,reason,note} plus release{released,releasedTool,heldMs,abandonedSeq,statementInterrupted,note}; pass cancel_inflight=true to ASK the in-flight call to stop, or release_inflight=true to FORCE-RELEASE the gate of a call that never came back (only when it is older than release_min_held_ms, default 60000). BOTH ARE BEST EFFORT: while a call holds the message-pump point no second call is executed - the request may not even be delivered - so the reliable exits are WAIT or terminate the VB6 process from outside. It also reports stateSource (ebMode / commandBars / ebMode+commandBars), commandBarsSuspended and notRunning, and clears a detected post-run suspended CommandBars window with ONE activate_component (autoRecover in the receipt) so a following attach call cannot mistake design for run. | open_project | Open a project file (.vbp) in the IDE (VBProjects.AddFromFile). Without exclusive it is added to the current workspace. SAME FILE, SEVERAL SPELLINGS: when the target .vbp is already open - including through an 8.3 short name, forward slashes, different case or a directory alias - the call SHORT-CIRCUITS: it returns alreadyOpen:true with the diskVsMemory comparison and does NOT close or re-add the project. When the on-disk .vbp no longer describes the in-memory project the call still answers alreadyOpen:true but with ok:false + reason=unsaved_changes_would_be_lost / disk_vs_memory_mismatch / project_saved_flag_unreadable + reloadRefused:true: the disk copy is NOT loaded and the in-memory project stays in use (remove_project then open_project to take the disk copy). 33b: a SUCCESSFUL open always carries ok:true; IDE API errors that did not stop the open are reported in apiWarnings[] (code/message/raw/phase), never in apiError. With exclusive:true, a DIRTY UNTITLED project would be written into the IDE current directory by the close path (measured); the call REFUSES by default with ok:false + reason=dirty_untitled_would_write + dirtyComponents/cwdCandidateFiles/zeroWriteBasis/... and writes nothing - pass allowHostWrite:true to allow that write and get it reported. | add_project | Create a new project in the IDE (VBProjects.Add) or from a template. | remove_project | Close (remove) a project from the IDE workspace. 33b: with allowDirty:true a DIRTY UNTITLED project (no file on disk) would be written into the IDE current directory by VB6 while closing (measured: 工程1.vbp/.vbw + component files, same-named files overwritten) and VBProject.Saved is read-only, so that call REFUSES unless allowHostWrite:true with ok:false + reason=dirty_untitled_would_write + dirtyComponents/cwdCandidateFiles/zeroWriteBasis/... | replace_code | Edit a component's code in IDE memory (line based). replace: overwrite start_line..end_line. insert: before start_line. append: after last line. delete: remove range. set: replace the whole module with code. replace and delete REQUIRE expected_sha256. The chosen remedy is the SHA PIN, not a proc: address space: a whole-pane sha detects ANY drift (a proc-relative address only detects drift across procedure boundaries within the same pane, and it would have to be re-derived from the very text it is meant to pin) - so a drifted pane is refused with sha256_mismatch + the current sha in one retry, and the receipt additionally echoes procBefore/procAfter{proc,startLine,endLine,firstLine,lastLine} so the targeted procedure is visible on both sides. (MEASURED; this is NOT an operation property - do not classify by op): whether the pane's final line break survives depends on (a) whether the BASE text already ended with one and (b) WHERE you insert. An insertion in the MIDDLE never touches the tail, so the result INHERITS the base's tail; an insertion at the END rebuilds the tail and normalises it. Measured: same operation (insert, exactly one trailing CRLF submitted) yields result ends_with_crlf=true on a base that already ended with CRLF (middle) and false on a base that did not. Never infer the outcome; the receipt's trailingBlankLine reports what actually happened and newTotalLines counts the way the caller's splitlines() does (a trailing break is not an extra line). the submitted block is checked BEFORE the write - a redundant trailing End <Sub/Function/Property> is refused as extra_procedure_end (with block line numbers, the header/End pairs it did match and a suggestedText), set/append must be self-contained (missing_procedure_end), and any edit that would leave the pane unbalanced is refused as predicted_procedure_imbalance instead of becoming a compile-time E105. Two further PRE-WRITE refusals replace the old silent clamping: an out-of-range replace/delete is refused as reason=range_beyond_end (it is NEVER downgraded to an insert, and deletedLines:0 is no longer a success signal), and an edit that would split a VB line continuation is refused as reason=inside_continuation. Text the ANSI code pane cannot represent is refused as reason=unencodable_text instead of being written with substituted characters. Component is marked unsaved; use save_project. Pass snapshot=true to write a pre-edit pane snapshot that undo_edit can restore (default false = no extra file write; set already snapshots by default). requestedRange has ONE shape per mode: {mode:"range", operation, start_line, end_line} here and in add_code / guard refusals, {mode:"anchor", anchor, occurrence, match, scope?} in edit_by_anchor, {mode:"anchor-batch", ops, match} in apply_edits (a multi-component batch answers {mode:"anchor-batch-multi", ops, components, match}) - branch on mode instead of guessing which shape arrived. |
| move_procedure | Move a WHOLE procedure block between components in ONE transaction: take the block from the SOURCE pane, insert it into the TARGET (after insert_anchor, or appended), then delete it from the SOURCE. A failure AFTER the first pane write rolls BOTH panes back (rolledBack:true, restoreVerified proves the read-back); a failure BEFORE any write (reason=proc_not_found / proc_range_out_of_bounds / insert_anchor_not_found) answers rolledBack:false + restoreVerified:false because nothing was written. insert_anchor is matched against TRIMMED target lines and the FIRST match wins. .vbp is never touched. Receipt: moved{from,to,proc,lineCount,insertAfterLine}, sourceSha256Before/After, targetSha256Before/After, rolledBack, restoreVerified, snapshots[], encoding/roundtrip_ok/bom, vbpTouched:false. |
| delete_procedures | Delete SEVERAL procedures in ONE transaction: a pre-edit _undo pane snapshot is written for every touched component (undo_edit can restore it); if any deletion fails every touched pane is restored. Receipt: deleted[]{component,proc,fromLine,toLine,lineCount}, snapshotId (a FIXED marker string, not a snapshot handle - list the real snapshots with undo_edit{action:'list'} and restore one by its ts), rolledBack, restoreVerified, shas[]. |
| edit_by_byte_anchor | Replace bytes in a file using GBK/ANSI RAW-BYTE anchors (base64 in, base64 out) - the only byte-exact edit path for mixed Chinese/ASCII sources. Refuses an anchor that would split a double-byte GBK character (lead 0x81..0xFE / trail 0x40..0xFE) with reason=anchor_splits_gbk_char; reports encoding_mismatch when the bytes are valid text but the file is not in that encoding. A round-trip self-check (decode->encode) runs BEFORE writing and a failure refuses the write (roundtrip_ok:false). Receipt: encoding, bom{...}, gbkBoundarySafe, anchorByteOffset, matches, sha256Before/After, bytesBefore/After, roundtrip_ok. |
| add_component | Create a new component in the active project with optional name and initial code. type=form is ALWAYS built through the synthesized .frm + AddFile route (the IDE's Add Form menu is never used): it writes <ProjectDir>\<name>.frm, is refused with reason=project_dir_unavailable when the project has no file on disk yet, and refused with reason=project_dir_write_not_allowed when project-directory writes are disabled. For the designer types form / mdiform / usercontrol the component IS created (the paired .frm and the .vbp are in sync), but this atomic path cannot manage the paired binary: the receipt carries pairedBinaryUnsupported:true + pairedBinaryReason whose text says "nothing was changed" - that statement is WRONG, something WAS changed - and its howToProceed says to call add_component again. Do NOT retry: a second add_component creates a DUPLICATE component. Materialise the paired binary with save_project instead. |
| remove_component | Remove a component from the project (VBComponents.Remove). Cannot be undone.
